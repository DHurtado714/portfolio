## The numbers nobody is talking about

In 2026, roughly **46% of all code written by active developers** comes from AI assistants. Tools like Claude Code, Cursor, Copilot, and Codex CLI are no longer autocomplete — they read your entire repository, design changes, write the implementation, and open pull requests.

The productivity numbers are real:

| Metric | Before AI | With AI agents |
|---|---|---|
| Lines of code per session | baseline | 3–5x |
| Cycle time (feature to PR) | baseline | 30–60% faster |
| Code churn rate | ~2–3% | 5.7–7.1% |
| Monthly token cost per engineer | $0 | $200–$2,000 |

Code churn is the one that should make every payments engineer stop and read again.

**Churn rate measures what percentage of code is rewritten or deleted within 2 weeks of being written.** It is a proxy for code quality and rework. If your churn goes up while your velocity goes up — you are shipping faster and rewriting more. In consumer apps that is annoying. In payments, it is a compliance and reliability risk.

**Documentation and comments**

ADRs, inline documentation, README updates — fast and decent. Low risk.

## Where it fails — and why churn is the signal

The failure modes cluster around **concurrency, idempotency, and financial state transitions** — exactly the problems that define payments work.

These are not random bugs. They are a predictable pattern.

AI models are trained on a distribution of code that is mostly CRUD applications, tutorials, and side projects. The tricky parts of payments engineering — atomic operations, distributed lock management, exactly-once semantics, settlement state machines — appear far less frequently in training data. The model generates plausible code that handles the happy path beautifully and silently breaks under load.

**The naive pattern AI reaches for:**

```typescript
// ❌ ROTO: race condition bajo carga concurrente
async processPayment(paymentId: string): Promise<void> {
  const payment = await this.paymentRepo.findOne({ where: { id: paymentId } });

  if (payment.status === PaymentStatus.PENDING) {
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.PROCESSING });
    await this.externalGateway.charge(payment);
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.COMPLETED });
  }
}
```

This looks completely correct. In a single-process, low-traffic scenario it works perfectly.

Under concurrent load, two workers can read `PENDING`, both pass the status check, and both fire the external charge. You just double-charged someone.

**The correct pattern:**

```typescript
// ✅ CORRECTO: optimistic lock + single atomic state transition
async processPayment(paymentId: string): Promise<void> {
  const result = await this.paymentRepo
    .createQueryBuilder()
    .update(Payment)
    .set({ status: PaymentStatus.PROCESSING, version: () => 'version + 1' })
    .where('id = :id AND status = :status AND version = :version', {
      id: paymentId,
      status: PaymentStatus.PENDING,
      version: currentVersion,
    })
    .execute();

  if (result.affected === 0) {
    // Someone else got there first — this is correct behavior
    return;
  }

  try {
    await this.externalGateway.charge(payment);
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.COMPLETED });
  } catch (err) {
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.FAILED });
    throw err;
  }
}
```

The difference is one atomic conditional update with an optimistic lock. AI does not reach for this pattern unless you explicitly prompt it with the right context and it understands your domain.

## The race condition I almost shipped

I was building a settlement reconciliation job. Claude Code generated a clean implementation that walked through open settlements, matched them against external ledger entries, and marked them reconciled.

It was fast. Tests passed. The code read beautifully.

What it missed: the job was scheduled to run on multiple ECS tasks simultaneously. Two instances could pick up the same settlement, reconcile it against the same ledger entry, and mark it twice — corrupting the audit trail.

The fix was a distributed lock at the settlement ID level using Redis before processing each record. Two lines of code. But only if you know to look for it.

Load testing caught it before production. Manual review had not — I had been looking at the logic, not the concurrency model.

That is the failure mode. Plausible logic, invisible risk under concurrency.

## A review framework for AI-generated payment code

I now treat AI-generated code for payments work like a PR from a brilliant junior engineer who has never worked in a financial system.

The review checklist for every AI-generated payments PR:

**Concurrency and race conditions**
- Does any read-then-write on a financial record use an atomic operation or optimistic lock?
- Can multiple workers process the same item simultaneously? What happens if they do?
- Are any shared counters or balances updated with non-atomic operations?

**Idempotency**
- Can this operation be retried safely?
- Is there an idempotency key or a unique constraint that prevents double-execution?
- What happens if the external call succeeds but the DB update fails?

**State machine integrity**
- Does the code validate that state transitions are legal? (PENDING → PROCESSING is valid; COMPLETED → PROCESSING is not)
- Are illegal transitions rejected at the database level, or only at the application level?

**Error handling and rollbacks**
- If step 3 of a 5-step flow fails, what state is the system in?
- Is there a compensating transaction or a retry mechanism?
- Does the error propagate in a way that allows upstream retry?

**Audit trail**
- Is every state change recorded with enough metadata for a compliance audit?
- Is the recording of the change part of the same transaction as the change itself?

## The skill gap in 2026

The productivity gap in 2026 is not between developers who use AI and developers who do not.

It is between developers who use AI and review with judgment, and developers who use AI and ship whatever it produces.

In a CRUD app or an internal tool, the cost of that gap is a bug and some rework. In a payments system processing real money across borders, it is a double charge, a corrupted ledger, or a compliance finding.

The tools are genuinely powerful. Claude Code today reads my entire payments repo, understands the domain models, and generates code that is correct for 80% of what I build.

That 20% is where the money is.

AI makes you fast enough that you have time to review everything carefully. Use that time.

Review AI output like it is a junior engineer's first PR on a mission-critical service. Because that is exactly what it is.

And I am still learning.
