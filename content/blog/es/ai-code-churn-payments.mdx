## Los números que nadie está discutiendo

En 2026, aproximadamente el **46% de todo el código escrito por desarrolladores activos** viene de asistentes de AI. Herramientas como Claude Code, Cursor, Copilot y Codex CLI ya no son autocompletado — leen todo el repositorio, diseñan cambios, escriben la implementación y abren pull requests.

Los números de productividad son reales:

| Métrica | Sin AI | Con agentes de AI |
|---|---|---|
| Líneas de código por sesión | base | 3–5x |
| Cycle time (feature a PR) | base | 30–60% más rápido |
| Tasa de churn de código | ~2–3% | 5.7–7.1% |
| Costo mensual de tokens por ingeniero | $0 | $200–$2,000 |

El churn de código es el que debería hacer que todo ingeniero de pagos pare y lo relea.

**El churn rate mide qué porcentaje del código se reescribe o elimina dentro de las 2 semanas de haber sido escrito.** Es un proxy de calidad de código y retrabajo. Si el churn sube mientras la velocidad sube — estás publicando más rápido y reescribiendo más. En aplicaciones de consumo eso es molesto. En pagos, es un riesgo de compliance y confiabilidad.

## Lo que AI hace bien en un stack de pagos

Uso Claude Code a diario en un sistema de pagos NestJS + AWS + TypeScript que maneja flujos cross-border en LATAM. Aquí dónde genuinamente acelera el trabajo:

**Boilerplate y scaffolding**

Generar módulos NestJS, DTOs, schemas Zod, entidades TypeORM — Claude Code lo hace en segundos y lo hace bien. La estructura es correcta, los imports resuelven, los tests se generan limpiamente.

```typescript
// Claude Code genera esto en un solo pass — correcto y completo
@Injectable()
export class PaymentIntentService {
  constructor(
    @InjectRepository(PaymentIntent)
    private readonly repo: Repository<PaymentIntent>,
    private readonly idempotencyService: IdempotencyService,
  ) {}

  async create(dto: CreatePaymentIntentDto, idempotencyKey: string): Promise<PaymentIntent> {
    return this.idempotencyService.wrap(idempotencyKey, () =>
      this.repo.save(this.repo.create(dto))
    );
  }
}
```

**Cobertura de tests**

Escribir suites de tests unitarios e integración es tedioso y de alto valor. Las herramientas de AI escriben el 80% correctamente. Yo reviso y ajusto los casos límite.

**Scripts de migración**

Migraciones de schema, backfills de datos, jobs de una sola vez — AI los hace rápido. Yo reviso el SQL. Siempre.

**Documentación y comentarios**

ADRs, documentación inline, actualizaciones de README — rápido y decente. Bajo riesgo.

## Dónde falla — y por qué el churn es la señal

Los modos de fallo se concentran en **concurrencia, idempotencia y transiciones de estado financiero** — exactamente los problemas que definen el trabajo en pagos.

Estos no son bugs aleatorios. Son un patrón predecible.

Los modelos de AI se entrenan en una distribución de código que es mayormente aplicaciones CRUD, tutoriales y proyectos personales. Las partes complicadas de la ingeniería de pagos — operaciones atómicas, gestión de locks distribuidos, semántica exactly-once, máquinas de estado de settlement — aparecen con mucha menos frecuencia en los datos de entrenamiento. El modelo genera código plausible que maneja el happy path de forma hermosa y falla silenciosamente bajo carga.

**El patrón naive al que llega la AI:**

```typescript
// ❌ ROTO: race condition bajo carga concurrente
async processPayment(paymentId: string): Promise<void> {
  const payment = await this.paymentRepo.findOne({ where: { id: paymentId } });

  if (payment.status === PaymentStatus.PENDING) {
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.PROCESSING });
    await this.externalGateway.charge(payment);
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.COMPLETED });
  }
}
```

Esto se ve completamente correcto. En un escenario de proceso único y bajo tráfico funciona perfectamente.

Bajo carga concurrente, dos workers pueden leer `PENDING`, ambos pasan el chequeo de estado, y ambos disparan el cobro externo. Acabas de cobrar dos veces a alguien.

**El patrón correcto:**

```typescript
// ✅ CORRECTO: optimistic lock + transición de estado atómica
async processPayment(paymentId: string): Promise<void> {
  const result = await this.paymentRepo
    .createQueryBuilder()
    .update(Payment)
    .set({ status: PaymentStatus.PROCESSING, version: () => 'version + 1' })
    .where('id = :id AND status = :status AND version = :version', {
      id: paymentId,
      status: PaymentStatus.PENDING,
      version: currentVersion,
    })
    .execute();

  if (result.affected === 0) {
    // Alguien más llegó primero — este es el comportamiento correcto
    return;
  }

  try {
    await this.externalGateway.charge(payment);
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.COMPLETED });
  } catch (err) {
    await this.paymentRepo.update(paymentId, { status: PaymentStatus.FAILED });
    throw err;
  }
}
```

La diferencia es una actualización condicional atómica con un optimistic lock. La AI no llega a este patrón a menos que la prompts explícitamente con el contexto correcto y entiende tu dominio.

## La race condition que casi publiqué

Estaba construyendo un job de conciliación de settlement. Claude Code generó una implementación limpia que recorría settlements abiertos, los emparejaba con entradas del ledger externo, y los marcaba como reconciliados.

Era rápido. Los tests pasaban. El código se leía de forma hermosa.

Lo que faltó: el job estaba programado para correr en múltiples tareas ECS simultáneamente. Dos instancias podían tomar el mismo settlement, conciliarlo contra la misma entrada del ledger, y marcarlo dos veces — corrompiendo el audit trail.

El fix fue un distributed lock a nivel de settlement ID usando Redis antes de procesar cada registro. Dos líneas de código. Pero solo si sabes dónde buscar.

El load testing lo capturó antes de producción. La revisión manual no — yo había estado mirando la lógica, no el modelo de concurrencia.

Ese es el modo de fallo. Lógica plausible, riesgo invisible bajo concurrencia.

## Un framework de revisión para código de pagos generado por AI

Ahora trato el código generado por AI para trabajo de pagos como un PR de un ingeniero junior brillante que nunca ha trabajado en un sistema financiero.

El checklist de revisión para todo PR de pagos generado por AI:

**Concurrencia y race conditions**
- ¿Algún read-then-write sobre un registro financiero usa una operación atómica u optimistic lock?
- ¿Pueden múltiples workers procesar el mismo ítem simultáneamente? ¿Qué pasa si lo hacen?
- ¿Hay contadores o balances compartidos que se actualicen con operaciones no atómicas?

**Idempotencia**
- ¿Puede esta operación reintentarse de forma segura?
- ¿Hay una idempotency key o un unique constraint que prevenga la doble ejecución?
- ¿Qué pasa si la llamada externa tiene éxito pero la actualización de DB falla?

**Integridad de la máquina de estado**
- ¿El código valida que las transiciones de estado sean legales? (PENDING → PROCESSING es válido; COMPLETED → PROCESSING no lo es)
- ¿Las transiciones ilegales se rechazan a nivel de base de datos, o solo a nivel de aplicación?

**Manejo de errores y rollbacks**
- Si el paso 3 de un flujo de 5 pasos falla, ¿en qué estado queda el sistema?
- ¿Hay una transacción compensatoria o un mecanismo de retry?
- ¿El error se propaga de forma que permita el retry upstream?

**Audit trail**
- ¿Cada cambio de estado se registra con suficiente metadata para una auditoría de compliance?
- ¿El registro del cambio es parte de la misma transacción que el cambio mismo?

## La brecha de habilidad en 2026

La brecha de productividad en 2026 no es entre desarrolladores que usan AI y desarrolladores que no.

Es entre desarrolladores que usan AI y revisan con juicio, y desarrolladores que usan AI y publican lo que sea que produce.

En una app CRUD o una herramienta interna, el costo de esa brecha es un bug y algo de retrabajo. En un sistema de pagos que procesa dinero real a través de fronteras, es un doble cobro, un ledger corrupto, o un hallazgo de compliance.

Las herramientas son genuinamente poderosas. Claude Code hoy lee todo mi repositorio de pagos, entiende los modelos de dominio, y genera código que es correcto para el 80% de lo que construyo.

Ese 20% es donde está el dinero.

AI te hace lo suficientemente rápido como para que tengas tiempo de revisar todo con cuidado. Usa ese tiempo.

Revisa el output de AI como si fuera el primer PR de un ingeniero junior en un servicio de misión crítica. Porque eso es exactamente lo que es.

Y sigo aprendiendo.
